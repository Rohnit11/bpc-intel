# /answer-gaps

Close the loop on questions the assistant could not answer: research them, land
the findings as governed data, and let the chatbot's knowledge grow — without
ever letting an unsourced claim in through the back door.

Run after the weekly harvest PR lands (see
`.github/workflows/harvest-questions.yml`), or any time
`docs/question-backlog.md` has open rows.

## Why this exists

The chatbot answers only from sourced DataPoints and refuses otherwise. Each
refusal is a signal about what the founding team actually needs and the research
doesn't yet cover — a demand-driven research backlog, generated by real usage
rather than guesswork.

## The one rule that matters

**An answer is not "text the chatbot can serve." It is data that passed the same
gate as everything else.** New quantitative claims go through
`lib/ingest/research_drop.py` (schema + taxonomy validation, real `source_url`
required, `value_basis` + `confidence` mandatory). Never write a figure straight
into a markdown file to make the chatbot look smarter — that would put unsourced
numbers next to governed ones with identical authority, which is precisely what
this system exists to prevent.

## Steps

1. **Read the backlog.** `docs/question-backlog.md` splits into:
   - **Research gaps** — nothing retrieved; genuinely missing data.
   - **Retrieval gaps** — data existed but the assistant declined. Fix these
     first and for free: they usually mean a missing synonym in
     `web/lib/retrieval.ts`'s `SYNONYMS` map, or an index field that isn't
     searchable. No research needed.

2. **Triage the research gaps.** Group by theme. Drop anything out of scope
   (not BPC, not KR/IN) — mark those `wont_fix` rather than researching them.

3. **Research in scope, per `commands/research.md`.** 3+ topics = parallel
   subagents. Every claim needs a URL you actually fetched.

4. **Land the findings:**
   - Quantitative → a drop file in `data/manual/research_drops/`, validated with
     `python -m lib.ingest.research_drop --check <file>`, then merged
     single-writer with `--all`.
   - Qualitative → `config/india_findings.yaml` or `config/corridor.yaml`, each
     bullet carrying its source and URL.
   - Interpretation → refresh the affected `/insights` reads. **Check whether
     new data makes an existing analyst read factually wrong** (e.g. a read that
     says "no data exists" for a segment that now has data) and rewrite it.

5. **Rebuild and verify:**
   ```
   python -m pytest && python -m lib.web_export
   ```
   `web_export` rebuilds `chat_index.json`, so the assistant picks up the new
   knowledge on the next deploy. Confirm the originally-unanswered question now
   answers — locally via `/ask`, or by reading the retrieved facts.

6. **Mark resolved.** Update the rows in Neon so they stop being re-harvested:
   ```sql
   UPDATE chat_questions
   SET status = 'researched', resolved_at = now(), resolution_ref = '<PR url>'
   WHERE id = ANY(ARRAY[<ids>]);
   ```
   (`markResolved()` in `web/lib/questions-db.ts` does the same from Node.)

7. **Commit + PR.** The diff shows exactly which claims entered the knowledge
   base and on what evidence — review it as data, not as prose.

## What NOT to do

- Do not answer a gap from model knowledge. If research finds nothing, say so
  and leave the row open with a note — a persistent gap is information.
- Do not soften a `LOW` confidence figure into a confident one to make the
  chatbot sound better.
- Do not delete questions to clear the backlog. Mark `wont_fix` with a reason.
